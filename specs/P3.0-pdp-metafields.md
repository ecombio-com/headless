# Spec: P3.0 PDP metafields (`pdp.*` namespace)

Plan item: `P3.0` in plan.md · Milestone: M2 (data work starts now) · Status: draft

## 1. Why
Product-page data is spread across 20 generic `custom.*` fields, some of them legacy
(page-based specs and FAQ) or scattered (three delivery-day fields). A dedicated `pdp.*`
namespace makes every product-page field easy to find, manage and audit, and gives the
Headless PDP one clean data contract before its UI is ported.

## 2. What
- Define the PDP fields under the `pdp` namespace on **dev (ecombio)** first, then **prod (khkkyb-b8)**.
- Copy existing values from `custom.*` to `pdp.*` with a script (no manual entry).
- Headless reads `pdp.*` first and falls back to `custom.*` until every product is copied.
- Merge scattered fields (delivery days) into one field.
- Remove the legacy fields once nothing reads them.

Not in scope: product-card fields (`custom.card_*`), collection, page and blog metafields.

## 5. Backend (data)
- Script: `scripts/pdp-namespace` (PowerShell): create definitions, copy values `custom → pdp`, report counts. Read-only `-DryRun` first. Dev store, then prod.
- Code: one query file for PDP fields; each field reads `pdp.*` with a `custom.*` fallback alias.
- Cache: unchanged (product-extras stays deferred, CacheLong).
- If a field is missing or fails its schema: the section hides; the page never crashes.

## 6. Frontend
No visible change in this task. The UI sections come in P3.1.
